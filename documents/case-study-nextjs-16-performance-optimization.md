# Оптимизация производительности Next.js 16: как мы вывели Core Web Vitals и PageSpeed в зеленую зону (LCP, CLS, font-display, preloading)

**Автор**: ant4x  
**Стек**: Next.js 16 (App Router), React 19, TypeScript, Tailwind CSS v4, Sharp  
**Результат**: Mobile PageSpeed **97/100**, Desktop PageSpeed **100/100**, TBT: **0 мс**, CLS: **0**, Accessibility: **100**

---

## Введение: конфликт эстетики и производительности

Современный премиальный веб-дизайн требует выразительной графики: полноэкранные фото, интерактивные эффекты наложения слоев, аккордеоны с галереями и благородную типографику (сочетание антиквы и гротеска). Однако для алгоритмов Google PageSpeed и стандартов Core Web Vitals такой сайт часто оказывается тяжелым испытанием.

При первичном аудите нашего проекта мы столкнулись с классической картиной:
- **Total Blocking Time (TBT)** на десктопе улетал в красную зону — **3 910 мс**.
- **Largest Contentful Paint (LCP)** на мобильных устройствах под эмуляцией Slow 4G доходил до **5.9 с**.
- **Размер первоначального HTML** раздулся до катастрофических **276 КБ** на компактном одностраничнике.
- **Интерактивные элементы** страдали от скрытых задержек: браузер тратил до 48 мс на каждый кадр движения мыши из-за принудительного пересчета макета (Forced Reflow), а картинки в аккордеонах мигали с опозданием в полсекунды.

Ниже подробный инженерный разбор того, как мы расследовали эти узкие места, опровергли несколько распространенных догм и вывели сайт в стабильную зеленую зону 97-100 баллов без единой визуальной уступки в дизайне.

## 1. Ликвидация TBT: как сократить блокировку главного потока с 1 760 мс до 0 мс

Total Blocking Time измеряет общее время между первой отрисовкой контента (FCP) и моментом, когда страница становится полностью отзывчивой на действия пользователя. Задачи длиннее 50 мс на главном потоке считаются длинными (Long Tasks) и напрямую штрафуют итоговый рейтинг.

В нашем профиле производительности Lighthouse категория «Other» в отчете *Minimize main-thread work* занимала более 2.1 секунды.

### Ошибка 1: Ловушка `placeholder="blur"` в `next/image`

`next/image` предоставляет возможность создавать эффект размытой предзагрузки с помощью статического импорта:
```tsx
// До оптимизации: казалось хорошей практикой
import heroPhoto from "@/assets/hero.jpg";

<Image 
  src={heroPhoto} 
  alt="" 
  placeholder="blur" 
  fill 
/>
```

**В чем была проблема:**
При статическом импорте Next.js во время сборки генерирует миниатюрную base64 Data URL строку и внедряет ее прямо в атрибут `style` тега `<img>`. Когда на странице находится 11 изображений (первый экран, галерея тура, карточки локаций), в тело HTML внедряется 22 длинных base64-строки.

Это привело к двум скрытым ударам по производительности:
1. **Раздутие HTML-документа**: вес страницы вырос с 14 КБ до 276.6 КБ. Пока медленная мобильная сеть скачивала эти 276 КБ сырого HTML, парсинг документа стоял на паузе.
2. **Синхронное декодирование**: Браузер был вынужден синхронно декодировать десятки base64-изображений и рассчитывать фоновые стили CSS до отрисовки первого полезного пикселя, блокируя CPU на 1.7 секунды.

**Решение:**
Мы полностью удалили `placeholder="blur"` с фоновых слоев и компонентов, находящихся ниже первого экрана. 
- Вес HTML мгновенно сократился с **276.6 КБ до 79.2 КБ (-71%)**.
- Мобильный TBT упал с **1 760 мс до 0-20 мс**.

### Ошибка 2: Принудительный синхронный пересчет макета (Forced Reflow)

В секции Hero реализован эффект проявления второго слоя пейзажа: при движении курсора мыши верхнее изображение срезается маской `clip-path: circle(...)`, открывая второе изображение под ним.

Исходный обработчик мыши выглядел так:
```tsx
// До оптимизации: Forced Reflow на каждый кадр
const handleMouseMove = (e: React.MouseEvent<HTMLDivElement>) => {
  const rect = e.currentTarget.getBoundingClientRect(); // ВЫЗЫВАЕТ FORCED REFLOW!
  const x = ((e.clientX - rect.left) / rect.width) * 100;
  const y = ((e.clientY - rect.top) / rect.height) * 100;
  setCoords({ x, y });
};
```

**В чем была проблема:**
Вызов `getBoundingClientRect()` внутри обработчика `onMouseMove` заставляет движок браузера немедленно прервать исполнение JavaScript, сбросить очередь отрисовки и принудительно пересчитать геометрию всего DOM-дерева в текущем тике. В профилировщике Chrome это вызывало пересчеты стилей длительностью 30-48 мс на каждый пиксель движения курсора.

**Решение:**
1. Размеры контейнера измеряются **один раз** при наступлении события `onMouseEnter` и сохраняются в `useRef`. При необходимости они обновляются только по событию ресайза окна.
2. Обновление координат маски вынесено в `requestAnimationFrame`:

```tsx
// Оптимизированный подход: 0 ms блокировки
const heroRectRef = useRef<DOMRect | null>(null);
const rafIdRef = useRef<number | null>(null);

const handleMouseEnter = (e: React.MouseEvent<HTMLDivElement>) => {
  heroRectRef.current = e.currentTarget.getBoundingClientRect();
};

const handleMouseMove = (e: React.MouseEvent<HTMLDivElement>) => {
  const rect = heroRectRef.current;
  if (!rect) return;

  const clientX = e.clientX;
  const clientY = e.clientY;

  if (rafIdRef.current) cancelAnimationFrame(rafIdRef.current);
  rafIdRef.current = requestAnimationFrame(() => {
    const x = ((clientX - rect.left) / rect.width) * 100;
    const y = ((clientY - rect.top) / rect.height) * 100;
    setCoords({ x, y });
  });
};
```
*Результат*: Замечание о Forced Reflow полностью исчезло из Lighthouse, анимация маски достигла стабильных 120 FPS.

### Ошибка 3: Избыточная гидратация чисто статических данных

Секция с описанием тарифов и дат (`Shifts.tsx`) содержала подробные описания программ, условия проживания, списки включенных опций и десятки SVG-иконок. Компонент был помечен директивой `'use client'`, поскольку внутри находилась логика предзаполнения формы связи.

**Проблема:**
Каждый килобайт текста и верстки внутри Client Component сериализуется Next.js в JSON-манифест страницы и отправляется на клиент для фазы гидратации. Процессор мобильного устройства тратил время на десериализацию статического текста, который никогда не меняется.

**Решение:**
Мы применили фундаментальный паттерн Server Components:
1. Компонент `Shifts.tsx` очищен от `'use client'` и стал Server Component. Все описания и SVG рендерятся сервером в чистый HTML.
2. Интерактивные кнопки («Забронировать», «Узнать даты») вынесены в микро-клиентский компонент `ShiftButtons.tsx` размером менее 1.5 КБ.
3. Баннер согласия на cookie (`CookieConsent.tsx`) переведен на инициализацию через `requestIdleCallback` с задержкой 800 мс, чтобы в первые секунды загрузки главный поток оставался на 100% свободным для рендера первого экрана.

## 2. Оптимизация LCP: сокращение с 5.9 с до 2.4 с

Largest Contentful Paint оценивает скорость рендеринга самого крупного видимого контентного блока (в нашем случае — фоновой фотографии в секции Hero). Для зеленой зоны метрика должна быть строго меньше 2.5 секунд.

### Конкуренция за первый сетевой пакет

При первичном аудите мы обнаружили парадоксальную вещь: на мобильных устройствах LCP-картинка начинала скачиваться только на 2-й секунде.

**Причины:**
1. **Конкурирующий `priority` на логотипе**: В шапке сайта на логотипе стоял флаг `priority`. В результате Next.js генерировал тег `<link rel="preload">` для векторного логотипа и для фонового фото одновременно. Браузер делил ограниченную пропускную способность мобильного соединения между двумя файлами.
2. **Параллельная загрузка скрытого слоя**: В секции Hero находилось два изображения: видимое (`heroTop`) и скрытое под маской (`heroBottom`). Браузер послушно скачивал оба тяжелых файла сразу.

**Решение:**
1. Убран `priority` со всех элементов, кроме единственного истинного LCP-элемента — `heroTop`.
2. Внедрен ленивый монтаж второго слоя: нижнее изображение `heroBottom` физически не рендерится в DOM при первоначальной загрузке. Оно монтируется только по первому событию пользовательского взаимодействия (`onMouseEnter` на десктопе или `onTouchStart` на мобильном) либо через `requestIdleCallback`. Во время синтетического теста PageSpeed второй файл даже не начинает скачиваться, экономя 140 КБ трафика.

---

### Тонкая настройка адаптивных размеров (`sizes` и `deviceSizes`)

PageSpeed выдавал предупреждение:
> *«This image file is larger than it needs to be (1600x1126) for its displayed dimensions (1335x998). Est savings: 66 KiB»*.

По умолчанию Next.js использует массив ширин экранов:
`deviceSizes: [640, 750, 828, 1080, 1200, 1920, 2048, 3840]`.

Когда десктопный вьюпорт Lighthouse с шириной 1335px запрашивал картинку с `sizes="100vw"`, оптимизатор Next.js проверял:
- `1200` — меньше чем 1335px (не подходит, будет замыливание).
- Следующий доступный шаг — `1920`.
- Исходный файл имел ширину 1600px, поэтому Next.js отдавал полный 1600px файл. Разница между 1600px и 1335px составляла 20%, что превышало допустимый порог Lighthouse в 10%.

**Решение:**
В `next.config.ts` мы расширили сетку устройств, добавив промежуточные десктопные разрешения:
```ts
// next.config.ts
const nextConfig: NextConfig = {
  images: {
    formats: ["image/avif", "image/webp"],
    deviceSizes: [384, 480, 640, 750, 828, 1080, 1200, 1366, 1440, 1600, 1920, 2048],
    qualities: [60, 75],
  },
};
```
Теперь браузер с экраном 1335px получает аккуратно сжатую копию шириной ровно 1366px, полностью ликвидируя замечание аудита.

Кроме того, для фонового фото Hero под темным полупрозрачным оверлеем мы установили `quality={60}`. Для человеческого глаза разница под градиентом незаметна, но вес файла уменьшился на **35%** (с 38 КБ до 24 КБ на мобильных устройствах).

## 3. Инфраструктурный парадокс: Vercel Edge против одноядерного VPS

В ходе тестирования мы столкнулись с неожиданной аномалией: при одинаковой кодовой базе на Vercel сайт показывал идеальные 97 баллов, а на собственном облачном сервере с Node.js (1 vCPU) первое открытие страницы десктопа зависало более чем на **10 секунд**.

### Расследование 10-секундного зависания

Профайлер сервера показал, что при первом холодном запросе с десктопа процесс Node.js загружал процессор на 100% в течение 10 056 мс.

**Причина:**
В конфигурации был указан формат `image/avif`:
```ts
formats: ["image/avif", "image/webp"]
```
Браузер отправляет заголовок `Accept: image/avif,image/webp,...`. Next.js видит поддержку AVIF и запускает библиотеку Sharp для транскодирования исходника в AVIF с разрешением 2048px. 

Кодирование AVIF в высоком разрешении на 1 процессорном ядре виртуальной машины — крайне ресурсоемкая операция. Пока сервер кодировал один 2048px AVIF-файл, весь event loop Node.js стоял намертво, не отвечая на входящие HTTP-запросы.

**Почему на Vercel это работает великолепно?**
У Vercel оптимизация картинок вынесена в специализированную бессерверную инфраструктуру с глобальным Edge-кэшированием. Транскодирование выполняется изолированными воркерами, а готовый AVIF кэшируется на сотнях CDN-узлов по всему миру, экономя 47 КБ на мобильных клиентах.

**Инженерный вывод:**
- **Для деплоя на Edge/CDN (Vercel, Cloudflare)**: формат `image/avif` обязателен — он дает максимальное сжатие и минимальный LCP.
- **Для деплоя на компактных VPS / Docker-контейнерах с 1-2 vCPU**: формат AVIF на лету опасен. Следует использовать `formats: ["image/webp"]` (кодирование WebP занимает всего 150-200 мс — в 50 раз быстрее) либо предварительно генерировать статические ассеты на этапе сборки.

## 4. UX против Performance: JIT Pre-decoding в аккордеоне

Секция программы тура содержит аккордеон из 6 пунктов. При клике на строку выпадающая панель раскрывается плавной шторкой с фотографией локации.

### Проблема «мигающей картинки»

Мы применили стандартную рекомендацию — поставили на изображения внутри аккордеона `loading="lazy"`.
Однако пользователи столкнулись с неприятным визуальным багом:
1. В закрытом состоянии строка аккордеона имеет нулевую высоту (`grid-template-rows: 0fr`).
2. Браузер видит элемент с нулевой геометрией и из-за `loading="lazy"` **вообще не начинает скачивать файл**.
3. Пользователь кликает на плашку. Начинается плавная CSS-анимация раскрытия (0.55 с).
4. Только в момент клика браузер осознает появление элемента в области видимости и инициирует сетевой запрос.
5. Скачивание и декодирование занимают 300-400 мс. В итоге шторка открывается пустой черной дырой, после чего картинка резко «выскакивает» перед глазами.

Почему нельзя просто поставить `loading="eager"`?
Потому что 6 полноцветных фотографий начнут загружаться синхронно со страницей, забьют канал передачи данных и обрушат мобильный LCP и TBT.

### Решение: Двухуровневый Just-In-Time Pre-warming

Мы создали механизм упреждающей подготовки изображений, незаметный для синтетических тестов PageSpeed:

1. **Intersection Observer на подходе**:
Секция аккордеона отслеживается наблюдателем с упреждающим отступом `rootMargin: "600px 0px"`. Когда пользователь листает страницу и приближается к секции на 600 пикселей, скрипт прогревает кэш браузера для картинок аккордеона:
```ts
const preloadImage = (src: string) => {
  const img = new window.Image();
  img.src = src;
  if ("decode" in img) {
    img.decode().catch(() => {}); // Распаковывает растр в видеопамять GPU заранее!
  }
};
```
2. **Hover-intent на десктопе**:
При наведении курсора на строку аккордеона (`onMouseEnter`) за 150–250 мс до клика запускается мгновенный декодинг конкретного изображения.
3. **Вызов нативного `img.decode()`**:
Метод `decode()` заставляет браузер асинхронно распаковать сжатый WebP/AVIF в память видеокарты в фоновом потоке. Когда шторка раскрывается, растр уже находится в памяти GPU — картинка проявляется с первого кадра анимации без единой миллисекунды задержки.

## 5. Нулевой CLS и стабильность типографики

Метрика Cumulative Layout Shift (CLS) измеряет визуальную стабильность страницы. Любой скачок элементов при загрузке штрафуется. Наш результат — **CLS = 0**.

### 1. Отказ от динамических `dvh` в пользу стабильных `lvh` и `svh`
В мобильных браузерах (Safari на iOS, Chrome на Android) панель адреса динамически сворачивается при прокрутке.
- Использование единиц `100dvh` (Dynamic Viewport Height) вызывало постоянный пересчет высоты секции Hero: фоновое фото визуально «прыгало» и масштабировалось, а текст сдвигался прямо под пальцем пользователя.
- Мы зафиксировали секцию с помощью `100lvh` (Large Viewport Height — стабильная высота без учета скрытия панелей), а внутренний текстовый контейнер ограничили `h-[100svh]` (Short Viewport Height с учетом открытой панели навигации). Скачки макета были полностью устранены.

### 2. Грамотная интеграция `next/font/google`
Мы используем два шрифта: гротеск `Golos Text` для UI и антикву `Lora` с акцентным курсивом для заголовков.
- Для обоих шрифтов в `layout.tsx` задан `display: "swap"`.
- Предзагрузка тяжелого начертания `Lora Italic` отложена, чтобы не конкурировать с критическим путем рендеринга прямого текста интерфейса.

## 6. Доступность (A11y) и математика цветового контраста WCAG AA

В ходе аудита Accessibility оценка составляла 96-97 баллов из-за предупреждения:
> *«Elements must have sufficient color contrast against background»*.

Проблема коснулась акцентного красного цвета бренда (`#DA291C`) и вспомогательных номеров строк (`.rowNum: #767069`) на теплом кремовом фоне страницы (`#f7f5f1`).

По стандарту WCAG AA для мелкого текста (менее 18pt или 14pt bold) коэффициент контрастности должен быть **не менее 4.5:1**.
- Цвет `#767069` на фоне `#f7f5f1` давал контрастность **4.43:1** (недобор всего 0.07 пункта до зеленой зоны!).
- Яркий красный `#DA291C` на 11px тексте давал пограничный показатель **4.51:1**, который при субпиксельном антиалиасинге в некоторых браузерах падал ниже нормы.

**Решение:**
1. Мы разделили палитру: яркий акцентный красный остался на крупных кнопках и акцентных плашках.
2. Для текстовых меток, надписей и подзаголовков введен токен `--color-accent-text: #b81d13` (глубокий карминный оттенок с контрастом **5.85:1** против светлого фона).
3. Цвет номеров шагов скорректирован до `#5e5853` (контраст **5.52:1**).
4. В мобильном меню закрытый оверлей снабжен атрибутами `invisible` и `inert`, чтобы скрытые ссылки не попадали в фокус-дерево экранных дикторов.
*Результат*: 100 из 100 баллов в категории Accessibility.

## Чек-лист для высоконагруженных Next.js проектов

1. **Не используйте `placeholder="blur"` вслепую**: на страницах с десятком изображений это превратит ваш HTML в мегабайты base64-мусора и заблокирует главный поток на фазе TBT.
2. **Никогда не вызывайте `getBoundingClientRect` в `onMouseMove`**: считывайте геометрию при входе курсора (`onMouseEnter`) и обновляйте анимации строго через `requestAnimationFrame`.
3. **Разгружайте первый сетевой пакет**: только один элемент на странице должен иметь `priority` — это LCP-кандидат. Скрытые слои и логотипы не должны конкурировать за первый транш трафика.
4. **Учитывайте ограничения среды деплоя**: динамический `image/avif` великолепен на Vercel/Cloudflare CDN, но способен намертво заблокировать одноядерный VPS при холодном старте.
5. **Для скрытых элементов используйте JIT-декодирование**: `loading="lazy"` внутри скрытых вкладок и аккордеонов создает задержку появления контента. Используйте связку Intersection Observer и нативного `img.decode()`.
6. **Проверяйте контрастность мелких шрифтов**: не полагайтесь на субъективное восприятие цветов — всегда проверяйте расчетный коэффициент контрастности по WCAG AA (минимум 4.5:1 для обычного текста).
